## Case 1: 공공데이터포털(KMA) 비표준 응답 규격 및 2026년 행정구역 개편 불일치 해결

### 1. 현상 및 문제 상황
- **증상 1 (태스크 크래시)**: Airflow 정기 실행 중 `collect_uv_wide` 태스크가 간헐적으로 `RuntimeError: KMA UV API 99`를 발생시키며 실패함.
- **증상 2 (대규모 결측치 발생)**: 에러를 방어한 후에도 광주광역시(5개 구), 전라남도(22개 시·군), 인천광역시(중구·동구·서구) 등 총 30개 행정구역에 대해 자외선 지수(UVI) 데이터가 수집되지 않고 누락되는 현상(결측률 ~12%) 발생.

### 2. 근본 원인 분석 (Root Cause Analysis)
1. **비표준 응답 코드(`resultCode: "99"`)의 이중 의미**:
   - 기상청 공공데이터 API 가이드상 정상 빈 응답은 `03 (NODATA)`이나, 생활기상지수(`LivingWthrIdxServiceV5`) API는 미등록 행정코드 조회 시 시스템 치명 에러가 아닌 일반 "검색결과 없음" 상황에서도 `resultCode: "99"`, `resultMsg: "검색결과가 없습니다. [...]"`를 반환함.
   - 기존 수집기는 `code not in ("00", "03")`을 시스템 장애로 판단하여 파이프라인 전체를 중단시킴.
2. **단기예보 vs 생활기상지수의 조회 파라미터 불일치**:
   - 단기예보·초단기실황 API는 기상청 고유 **격자 좌표(`nx, ny`)**를 조회 키로 사용하여 행정구역 코드 변경의 영향을 받지 않음.
   - 반면 생활기상지수 API만 유일하게 **행정구역 코드(`areaNo`)**를 파라미터로 요구함.
3. **2026년 행정구역 개편 코드 선반영 불일치**:
   - 프로젝트 기준 행정경계 데이터는 국토정보플랫폼의 2024년 법정동코드(광주 `29...`, 전남 `46...`, 인천 중구 `28110...`, 동구 `28140...`)를 기반으로 함.
   - 그러나 기상청 생활기상지수 V5 내부 DB에는 **2026년 행정구역 개편안**이 이미 적용되어 있었음:
     - **광주(`29`) + 전남(`46`) 통합** → **`12` (전남광주통합특별시)** 코드로 전면 개편 (`12110... ~ 12870...`)
     - **인천 행정구역 개편**: 중구·동구 통합 → 제물포구(`2812500000`), 서구 분구/개편 → `2829000000`
   - 이로 인해 기상청 서버에서는 기존 2024년 코드가 존재하지 않는 지역으로 취급되어 30개 시군구가 통째로 결측됨.

### 3. 해결 전략 및 구현
- **비표준 99 응답 핸들링**: `_items_from_text` 함수에서 `code == "99"`이면서 메시지에 "검색결과가 없습니다"가 포함된 경우 치명적 에러 대신 정상 빈 리스트(`[]`)로 처리하도록 수정.
- **`AREA_CODE_ALIAS` 매핑 테이블 구축**:
  - 구 법정동코드 30개(광주 5개, 전남 22개, 인천 3개)를 기상청 V5 신규 행정지점코드로 1:1 자동 변환하는 매핑 딕셔너리 구축.
  - 상위 시도 코드(광역코드) 폴백 메커니즘을 결합하여 향후 행정구역 코드 변경 시에도 유연하게 대처하도록 설계.

```python
# weather_risk_assessment/collectors/uv_forecast.py
AREA_CODE_ALIAS: Dict[str, str] = {
    # 인천 제물포구 및 서구 개편 반영
    "2811000000": "2812500000", "2814000000": "2812500000", "2826000000": "2829000000",
    # 전남광주통합특별시(12) 광주 권역
    "2911000000": "1221000000", "2914000000": "1224000000", "2915500000": "1227000000", ...
    # 전남광주통합특별시(12) 전남 권역
    "4611000000": "1211000000", "4613000000": "1213000000", ...
}
```

### 4. 성과 및 의의
- 전국 **247개 전 행정구역 결측률 0% 달성** (247개 전 지역 100% 정상 수집 확인).
- 외부 API 공급자의 비표준 응답 규격 및 행정 체계 변경에 탄력적으로 대응하는 견고한 인제스천(Ingestion) 파이프라인 완성.

## Case 2: 메달리온 아키텍처 오염 방지를 위한 '사전 데이터 계약(Data Contracts)' 구축

### 1. 현상 및 문제 상황
- 외부 기상청 API는 가끔 점검 중이거나 장애 발생 시 빈 페이로드나 잘못된 날짜(과거 날짜 데이터), 또는 깨진 JSON을 반환함.
- 수집기가 불량 데이터를 그대로 S3 Bronze 레이크에 업로드할 경우:
  1. 잘못된 날짜 파티션이 S3에 생성되어 수동 삭제 작업 필요
  2. 다운스트림 PySpark 작업(Silver 정제, Gold 집계)이 런타임에 실패하거나, 잘못된 위험도가 계산되어 현업에 왜곡된 Slack 알림이 발송되는 문제 발생.

### 2. 해결 전략: In-Flight Data Contracts 검증
- **Bronze 업로드 전 엄격한 계약 검증 배치**: 수집된 데이터를 S3에 쓰기 직전, 로컬 스테이징 상태에서 스키마, 컬럼 타입, 시간대, 결측 범위를 검증하는 `validate_bronze_partition` 레이어 구축.
- **데이터 신선도(Freshness) 계약 적용**: 기상청의 `baseDate/baseTime`이 현재 파이프라인 실행 시각보다 4시간을 초과해 오래된 경우 S3 업로드를 즉시 차단(Fail-Fast).
- **Silver/Gold 계약 검증**: Spark 변환 후에도 위험도 범위(`0.0 <= R <= 1.0`), 시각·지역별 유일성(Uniqueness), 필수 지표 존재 여부를 단언(Assert)하여 데이터 품질을 보증.

```text
[KMA API 수집]
       ↓ (로컬 디렉터리 저장)
[Bronze Data Contract 검증] ──(불합격 시 즉시 중단)──> S3 오염 차단 & 알림
       ↓ (합격 시에만 업로드)
[S3 Bronze Parquet]
       ↓
[PySpark Silver/Gold Transform]
       ↓
[Medallion Contract 검증] ──(불합격 시 저장 차단)
       ↓
[S3 Delta Lake / Export Parquet]
```

### 3. 성과 및 의의
- **Bad Data 유입 원천 차단**: S3 데이터 레이크로의 불량 파티션 유입률 0% 유지.
- **Fail-Fast 아키텍처**: 오류 발생 시점을 수집 직후로 앞당겨(Shift-Left) 디버깅 비용 및 불필요한 분산 컴퓨팅(Spark) 비용 절감.

## Case 3: 대용량 지리 데이터(SHP) 파싱 병목 해소와 증분 캐싱 최적화

### 1. 현상 및 문제 상황
- 기상 데이터를 격자(`nx, ny`)로 변환하기 위해 전국 행정경계 SHP 파일(압축 해제 시 수백 MB)을 읽어 각 시군구의 중심점(Centroid)과 격자 번호를 매핑해야 함.
- 초기 구조에서는 매시 10분마다 실행되는 DAG의 첫 태스크(`make_admin_centroids_from_shp`)가 매시간마다 동일한 SHP 파일을 반복해서 읽고 GIS 연산을 수행함.
- 이로 인해 파이프라인 실행마다 불필요한 메모리 급증 및 1분 이상의 지연 시간(Latency)이 낭비됨.

### 2. 해결 전략: 파일 mtime 기반 캐싱 메커니즘
- 행정경계 데이터는 국토정보플랫폼의 고정 데이터이므로 코드가 수정되거나 원본 SHP가 변경되지 않는 한 결과는 항상 동일함.
- `weather_risk_assessment/paths.py`에 원본 소스 파일들의 최종 수정 시각(`mtime`)과 타깃 결과물의 `mtime`을 비교하는 `outputs_are_current` 함수 구현.
- 원본 SHP, 변환 스크립트 파일의 수정 시각보다 결과 CSV/Parquet이 최신인 경우, 무거운 GIS 연산을 즉시 스킵하고 기존 결과물을 재사용.

```python
# weather_risk_assessment/paths.py
def outputs_are_current(outputs: Iterable[Path], sources: Iterable[Path]) -> bool:
    # 산출물이 존재하고, 모든 산출물의 수정 시각이 모든 소스 파일보다 최신이면 재사용
    ...
```

### 3. 성과 및 의의
- 정기 파이프라인 실행 시 행정구역 생성 태스크 소요 시간을 **~45초에서 0.05초(즉시 재사용)로 단축**.
- 컨테이너 메모리 스파이크를 방지하여 Airflow 워커 리소스 안정성 확보.

## Case 4: 아키텍처 군살 빼기 (Kafka 오버엔지니어링 제거 및 직접 알림 전환)

### 1. 현상 및 문제 상황
- 초기 설계에는 알림 처리를 위해 Kafka 브로커와 토픽이 포함되어 있었음.
- 그러나 본 프로젝트는 **1시간 주기 배치 파이프라인**이며, 알림 대상은 시간당 247개 행정구역 중 위험도 `HIGH(>=0.6)` 이상인 소수(수 개~십수 개) 지역에 불과함.
- 초당 수만 건을 처리하는 Kafka 클러스터는 유지보수 오버헤드, Zookeeper/KRaft 관리, Docker 리소스 낭비(RAM 1~2GB 점유)를 초래하는 전형적인 **오버엔지니어링(Over-engineering)**이었음.

### 2. 해결 전략: YAGNI(You Aren't Gonna Need It) 원칙 적용
- Kafka 클러스터 및 관련 스트리밍 의존성을 과감히 제거.
- Spark Gold 집계 완료 후, 가벼운 Python 태스크(`send_high_risk_alerts`)에서 Slack Incoming Webhook API를 직접 호출하도록 구조 단순화.
- 웹훅 주소 누출 방지를 위한 보안 처리 및 타임아웃, 지수 백오프(Exponential Backoff) 재시도 로직을 내장한 `slack_alert.py` 구현.
- DAG 실패 콜백(`on_failure_callback`)을 연동하여 작업 실패 시에도 Airflow 로그 링크와 함께 Slack으로 즉시 알림 발송.

### 3. 성과 및 의의
- **인프라 복잡도 대폭 감소**: Docker Compose 서비스 수 감소로 로컬/CI 메모리 점유율 40% 이상 절감.
- **운영 안정성 향상**: 불필요한 분산 큐 장애 포인트를 제거하고 파이프라인 디버깅 경로를 일원화.

## Case 5: Airflow 3 런타임 전환 및 컨테이너 격리 안정화

### 1. 현상 및 문제 상황
- Airflow 버전을 최신 3.x(`3.3.2`) 계열로 업그레이드하는 과정에서 여러 호환성 이슈 발생:
  1. 공식 3.x 베이스 이미지에서 기존 초기화에 사용되던 `gosu` 유틸리티가 제거되어 컨테이너 권한 초기화 실패.
  2. Airflow 2의 레거시 import 경로(`airflow.operators.python_operator`) 사용으로 인한 경고 및 호환성 위험.
  3. 로컬 테스트용 MinIO Compose와 메인 Airflow Compose 간의 기본 프로젝트 네임스페이스 충돌로 컨테이너 네트워크 간섭 발생.

### 2. 해결 전략
- **권한 체계 현대화**: `gosu`에 의존하던 래퍼 스크립트를 제거하고, Airflow 공식 권장 방식인 UID 기반 비루트(Non-root) 실행(`AIRFLOW_UID`)으로 Dockerfile 및 Compose 정비.
- **네임스페이스 및 환경변수 격리**:
  - `docker-compose.yaml` 및 `docker-compose.minio.yaml`에 명시적인 `name` 속성을 부여하여 프로젝트 간 볼륨/네트워크 격리.
  - 최신 Airflow 공식 import 경로(`airflow.providers.*`, `airflow.operators.python.PythonOperator`)로 전면 마이그레이션.

### 3. 성과 및 의의
- 최신 Airflow 3.x 환경에서의 무결점 가동 및 배포 재현성 확보.
- CI 파이프라인에서 실제 Docker 빌드 및 테스트를 통과하는 프로덕션급 컨테이너 환경 완성.
