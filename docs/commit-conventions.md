# 커밋 규칙

이 문서는 사람과 자동화 에이전트가 동일한 기준으로 로컬 커밋을 만드는 데 사용한다.
각 커밋은 독립적으로 검토할 수 있고 가능한 한 검증을 통과한 상태여야 한다.

## 메시지 형식

```text
<type>(<scope>): <summary>
```

`type`과 `scope`는 영문 식별자를 사용하고 `summary`와 본문은 한국어로 작성한다.
`scope`는 의미가 분명할 때만 사용하며 제목은 72자 이내, 마침표 없이 작성한다. 변경
이유나 마이그레이션 정보가 제목만으로 충분하지 않으면 한국어 본문에 기록한다.

사용 가능한 `type`은 다음과 같다.

| type | 사용 시점 |
|---|---|
| `feat` | 데이터 파이프라인 기능 추가 |
| `fix` | 잘못된 동작이나 데이터 오류 수정 |
| `refactor` | 외부 동작을 유지하는 구조 개선 |
| `perf` | 처리 속도, 메모리, API 호출량 개선 |
| `test` | 테스트와 fixture만 변경 |
| `docs` | 문서만 변경 |
| `build` | 의존성, 패키징, Docker 이미지 빌드 변경 |
| `ci` | CI 워크플로 변경 |
| `chore` | 기능과 무관한 저장소 설정·관리 작업 |
| `revert` | 이전 커밋 되돌리기 |

권장 `scope`는 `dag`, `collector`, `bronze`, `silver`, `gold`, `risk`, `alert`,
`docker`, `docs`, `ci`다. 목록에 없는 scope도 변경 범위를 더 정확히 나타내면 사용할 수 있다.

예시:

```text
feat(bronze): 업로드 전 수집 데이터 계약 검증 추가
fix(collector): Airflow 실행 시각 기준 예보 슬롯 계산 수정
test(collector): KMA 대표 응답 fixture 추가
ci: Python 테스트 자동 실행 추가
docs: 로컬 데이터 디렉터리 구조 문서화
```

호환성을 깨는 변경은 `feat(scope)!:`처럼 `!`를 표시하고 본문에 영향과 이전 방법을
기록한다. 실제 이슈가 있을 때만 본문에 `Refs #123` 또는 `Closes #123`을 사용한다.

## type과 scope 자동 선택

에이전트는 사용자에게 type이나 메시지를 매번 묻지 않고 diff의 주목적에 따라 다음
우선순위로 결정한다.

1. 기존 동작이나 데이터가 잘못된 문제를 고치면 `fix`다.
2. 새로운 수집·변환·검증·알림 기능을 제공하면 `feat`다.
3. 결과를 유지하면서 코드 구조만 개선하면 `refactor`다.
4. 결과를 유지하면서 성능만 개선하면 `perf`다.
5. GitHub Actions 등 자동화 워크플로만 바꾸면 `ci`다.
6. 의존성, 패키징, Docker 이미지 생성 방식을 바꾸면 `build`다.
7. 테스트 또는 fixture만 바꾸면 `test`다.
8. 문서만 바꾸면 `docs`다.
9. 위 항목에 속하지 않는 저장소 관리 작업은 `chore`다.

기능 구현에 테스트와 문서가 함께 포함되면 주목적인 `feat` 또는 `fix`를 사용한다.
여러 영역을 함께 바꿔 하나의 정확한 scope를 고르기 어려우면 억지로 `project` 같은
scope를 만들지 않고 scope를 생략한다.

scope는 변경의 중심 영역을 기준으로 선택한다.

- Airflow 정의와 의존성: `dag`
- KMA 수집과 파싱: `collector`
- 데이터 레이크 계층: `bronze`, `silver`, `gold`
- 위험도 계산: `risk`
- Slack 알림: `alert`
- 컨테이너 실행 환경: `docker`
- 자동화 워크플로: `ci`

## 커밋 범위

- 서로 무관한 변경을 한 커밋에 섞지 않는다.
- `.env`, 인증정보, 실제 API 응답 원본, 생성 데이터, 캐시 파일은 커밋하지 않는다.
- 다른 사람이 만들었거나 현재 작업과 무관한 변경은 스테이징하지 않는다.

에이전트는 파일 개수가 아니라 변경 목적을 기준으로 커밋을 나눈다.

- 기능 코드와 그 기능을 검증하는 테스트는 같은 커밋에 둔다.
- 독립적인 테스트 인프라나 fixture만 추가하면 `test` 커밋으로 분리한다.
- 기능에 직접 필요한 짧은 문서는 같은 커밋에 포함할 수 있다.
- 독립적인 CI, 대규모 문서 정리, 기계적인 파일 이동은 별도 커밋으로 나눈다.
- 리팩터링과 동작 변경이 각각 독립적으로 검증 가능하면 별도 커밋으로 나눈다.
- 중간 커밋이 실행 불가능하거나 테스트를 깨뜨리도록 억지로 분할하지 않는다.

## 자동 커밋 절차

사용자가 코드 변경을 요청한 경우, 에이전트는 하나의 검토 가능한 작업이 완료되고 관련
검증이 통과하면 추가 확인 없이 로컬 커밋을 만든다. 사용자가 커밋하지 말라고 요청하면
그 지시를 우선한다.

1. `git status --short`와 diff를 확인해 현재 작업에서 만든 변경을 식별한다.
2. 관련 테스트와 저장소 기본 검증을 실행한다.
3. 현재 작업에 속한 파일 또는 hunk만 명시적으로 스테이징한다. `git add .`와
   `git add -A`는 사용하지 않는다.
4. `git diff --cached --check`와 `git diff --cached`로 커밋 내용을 다시 확인한다.
5. 변경이 여러 목적이면 각 커밋이 검증 가능한 상태를 유지하도록 나눈다.
6. 커밋 후 hash, 메시지, 수행한 검증, 남아 있는 uncommitted 변경을 보고한다.

관련 테스트가 실패하거나 현재 작업과 기존 변경을 안전하게 분리할 수 없으면 자동
커밋하지 않는다. 실패 원인과 커밋하지 않은 이유를 보고한다. 사용자가 명시적으로
요청하지 않는 한 `--amend`, rebase, push, merge, tag 생성은 수행하지 않는다.
