# 완료된 작업 커밋

사용자는 완료된 저장소 작업의 로컬 커밋을 허용했다. 이 권한에는 push, merge, rebase,
amend, tag 생성, 배포가 포함되지 않는다.

## 메시지 작성

제목은 `<type>(<scope>): <summary>` 형식으로 작성한다. `scope`가 불분명하거나 여러
영역에 걸치면 `<type>: <summary>`처럼 생략한다.

- `type`과 `scope`는 영문 소문자를 사용한다.
- `summary`와 본문은 한국어로 작성한다.
- `summary`는 72자 이내로 작성하고 마침표를 붙이지 않는다.
- `summary`는 `추가`, `수정`, `분리`, `제거`, `개선`처럼 변경 결과가 드러나게 쓴다.
- `작업`, `수정 사항 반영`, `업데이트`처럼 내용을 알 수 없는 표현은 사용하지 않는다.

diff의 주목적을 기준으로 type을 자동 선택한다.

| type | 선택 기준 |
|---|---|
| `feat` | 새로운 수집·변환·검증·알림 기능 추가 |
| `fix` | 잘못된 동작이나 데이터 오류 수정 |
| `refactor` | 외부 동작을 유지하는 코드 구조 개선 |
| `perf` | 처리 속도, 메모리, API 호출량 개선 |
| `test` | 테스트 또는 fixture만 변경 |
| `docs` | 문서만 변경 |
| `build` | 의존성, 패키징, Docker 이미지 빌드 변경 |
| `ci` | GitHub Actions 등 CI 워크플로 변경 |
| `chore` | 기능과 무관한 저장소 설정·관리 작업 |
| `revert` | 이전 커밋 되돌리기 |

버그 수정에 테스트와 문서가 포함되면 `fix`, 기능 추가에 테스트와 문서가 포함되면
`feat`를 사용한다. 중심 영역이 하나면 `dag`, `collector`, `bronze`, `silver`, `gold`,
`risk`, `alert`, `docker`, `ci` 중 scope를 선택한다. 더 정확한 이름이 있으면 새 scope를
사용할 수 있으며, 억지로 포괄적인 scope를 만들지는 않는다.

예시:

```text
feat(bronze): 업로드 전 수집 데이터 계약 검증 추가
fix(collector): 실행 시각 기준 예보 슬롯 계산 수정
ci: Python 테스트 자동 실행 추가
docs: 로컬 데이터 디렉터리 구조 문서화
```

제목만으로 변경 이유와 영향이 충분하면 본문을 생략한다. 다음 중 하나에 해당하면 제목
아래에 빈 줄을 두고 한국어 본문을 작성한다.

- 코드만 보고 알기 어려운 문제 원인이나 설계 선택이 있다.
- 데이터 스키마, 파티션, 호환성, 운영 방법이 달라진다.
- 대안 중 하나를 선택한 이유나 알려진 제한이 있다.
- 마이그레이션이나 후속 작업이 필요하다.

본문은 코드 목록을 반복하지 않고 `왜 변경했는지`, `동작이나 데이터가 어떻게 달라지는지`,
`주의할 영향은 무엇인지`를 설명한다. 필요한 경우 마지막 문단에 `Refs #123`,
`Closes #123`을 기록한다. 호환성을 깨는 변경은 제목의 type 뒤에 `!`를 붙이고
`BREAKING CHANGE: <한국어 설명>` footer를 작성한다.

본문 예시:

```text
feat(bronze): 업로드 전 수집 데이터 계약 검증 추가

필수 컬럼이나 키가 손상된 파일이 정상 파티션으로 저장되는 문제를 막는다.
태풍과 UV의 정상적인 빈 결과는 경고로 허용하고 파일 누락과 구분한다.

Refs #2
```

## 커밋 분리

- 서로 무관한 변경을 한 커밋에 섞지 않는다.
- 기능 코드와 그 기능을 검증하는 테스트는 같은 커밋에 둔다.
- 기능에 직접 필요한 짧은 문서는 같은 커밋에 포함할 수 있다.
- 독립적인 CI, 대규모 문서 정리, 기계적인 파일 이동은 별도 커밋으로 나눈다.
- 리팩터링과 동작 변경이 각각 독립적으로 검증 가능하면 별도 커밋으로 나눈다.
- 중간 커밋이 실행 불가능하거나 테스트를 깨뜨리도록 억지로 분할하지 않는다.

## 실행 절차

1. `git status --short`와 staged·unstaged diff를 확인해 현재 작업과 기존 변경을 구분한다.
2. 변경에 맞는 검증을 실행한다. 사용자가 WIP 커밋을 명시하지 않았다면 실패가 확인된
   구현을 커밋하지 않는다.
3. 하나의 목적에 해당하는 파일이나 hunk만 명시적으로 스테이징한다. `git add .`와
   `git add -A`는 사용하지 않는다.
4. `git diff --cached --check`, `git diff --cached`, 커밋 메시지를 검토한다. `.env`,
   인증정보, 실제 API 응답 원본, 생성 데이터, 캐시, 무관한 변경을 포함하지 않는다.
5. 위 규칙에 따라 type, scope, 제목과 필요한 본문을 자동 작성해 로컬 커밋한다.
6. 커밋 hash와 제목, 수행한 검증, 의도적으로 남긴 변경을 보고한다.

현재 작업을 기존 변경에서 안전하게 분리할 수 없으면 소유권을 추측하지 말고 커밋하지
않은 채 겹치는 내용을 설명한다.
